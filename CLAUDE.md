# Twins Tracker — context for Claude

Static PWA (no build step) for parents to chart twin NICU babies' nightly weights and PO feeds. Hosted on GitHub Pages from `main` / root. Backend: Firebase Auth (email/password, sign-up allowed) + Firestore. Multi-family: each family's data lives under `households/{hid}`; both parents join the same family with an invite code.

**This repo is public. Never commit names, birth dates/times, weights or any feed data.** All personal details live in Firestore (`households/main/config/profile`), entered on the in-app setup screen.

## Files
- `index.html` — the whole app (UI, charts via Chart.js 4.4.1 from cdnjs, all logic). Talks to the backend only through `window.Store`.
- `firebase-store.js` — implements `window.Store` on Firebase (offline cache on; writes resolve after server ack or 1.5 s). Fires `store-ready`. Collection names live in one place (`SHARED`, `PRIVATE`, `CONFIG`, exposed as `Store.lists`). A dormant test hook (`window.__FIREBASE_EMULATORS__`, set only by `tests/rules/store.test.js`) points it at the local emulators; the app never sets it.
- `firebase-config.js` — Firebase web config (not secret).
- `firestore.rules` — family membership rules (see Families). The original family `households/main` can also be claimed by the allowlisted emails (placeholders in the repo; real ones only in the console). Tested in `tests/rules/` against the emulator.
- `sw.js` — app-shell cache, network-first. Bump `CACHE` name when shell files change.
- `fonts/inter-latin-var.woff2` — Inter variable font (latin, self-hosted, OFL; licence in `fonts/LICENSE-Inter.txt`). Cached with the shell for offline.
- `manifest.webmanifest`, `icons/`.
- `privacy.html` — privacy policy (linked from sign-in and Settings; points to More → Settings → Family). `SUPPORT_EMAIL` placeholder must be replaced before release.
- `native/` — iOS wrapper (Capacitor 6). `npm run build` copies the web app into `native/www` with Chart.js and Firebase bundled locally (no service worker in iOS web views, so offline needs local files); `npm run sync` then copies into `ios/`. iPhone only, portrait. `appId` in `capacitor.config.json` is a placeholder (`com.example.twinstracker`). Build/sign/submit needs a Mac with Xcode and an Apple Developer account. `firebase-store.js` uses `initializeAuth` (no popup/redirect iframe) so auth works in the web view.

## Families
- `users/{uid}` → `{hid}` (which family this sign-in uses). `households/{hid}` → `{owner, code, codeExp (ms), created}`. `households/{hid}/members/{uid}` → `{email, t, code?}`. `invites/{CODE}` → `{hid, exp}` (get-only lookup, 8 chars from an unambiguous alphabet, 7 days).
- `Store.family()` resolves the family after sign-in: users doc → membership check; else claims `main` (allowlisted emails); else null → the app shows `#family` (join with code / start a new family). If `users/` is denied (old rules) it falls back to `main`; offline it reopens the cached hid.
- `Store.createFamily / joinFamily(code) / familyInfo / newInvite / removeMember(uid) / leave / deleteAccount(password)`. Settings → Family card: members (you / owner), invite code with Share + New code, Remove (owner), Leave, Delete my account (re-auth; the last member out deletes all the family's data). Ownership passes to another member when the owner leaves.
- Rules: data readable/writable only by members (or allowlisted emails for `main`); join only as yourself with the current unexpired code; members can't be edited; only the owner removes others or deletes the family record. The shared-data catch-all excludes `members`, `private` and `revoked`. **Legacy revocation:** removing a member of `main` writes `households/main/revoked/{email lowercased}` (owner only; members can't edit or delete it); `legacy()` ignores revoked emails, so the allowlist can't readmit them (claim, data access, creating the family record). The owner can still deliberately re-invite them with a code.
- **Store additions (Phase 1):** `patch(name, id, fields)` — merge only those fields into an existing family doc (`updateDoc`; fails/`store-error` rather than recreating a doc the other parent deleted; `by` is stripped so authorship never changes). `watchPrivate(name, cb, err)` / `putPrivate(name, id, rec)` / `removePrivate(name, id)` — like `watch`/`put`/`remove` but under the signer's own `private/{auth uid}/{name}` (uid always from Firebase Auth; `putPrivate` stamps `by` unless present). `lists` — `{shared, private, config}`. The stub (`tests/stub-store.js`) keeps private data per user (`__db.private[uid]`) and simulates removal (`__TEST_REMOVED`, `__TEST_CLEANUP_FAILS`).
- **Private subtree** `households/{hid}/private/{uid}/{name}/{doc}` (Phase 3 check-ins; `Store.lists.private` = `["checkins"]`): only the uid in the path can touch it — never the other parent, strangers, or the legacy allowlist. Read/list and delete need only "my uid" (the removed-member cleanup exception); create/update also need current membership.
- **Lifecycle (D10: a leaving or removed member's private data is deleted):** `purgePrivate(hid, uid)` deletes the signer's own private docs (server reads, explicit list, verifies empty). `leave()`: purge → transfer ownership → delete membership → delete pointer (pointer last, so a part-way failure is finished by the next open). Lifecycle decisions use `familyStrict()` (server reads, errors propagate) — never the lenient `familyInfo()`. `removeMember(uid)` (owner), fails closed in this order: publish a new invite code and read it back from the server (`rotateInvite(true)`; changing the family's code is what invalidates the old one) → delete the old invite doc → `main` only: write the revocation → delete the membership. Any error stops before access is revoked. `family()`: membership is checked with `getDocFromServer`; if it can't be confirmed (offline/error) nothing is deleted and the cached family reopens; if confirmed removed → purge own private data → delete `users/{uid}` → return null. If the purge fails it throws `cleanup-pending` (banner) and keeps the pointer, so the next open retries. `deleteAccount` fails closed: no swallowed errors; the Firebase Auth user is deleted only after all Firestore cleanup succeeded. Last member: purge → every `SHARED` collection (incl. `events`, `needs`) → config → invite (if it still exists) → revocations + family record (if it exists) → membership → pointer → auth user. Otherwise `leave()` then the auth user. Every step is safe to repeat; if the membership is already gone, the next open's `family()` finishes the pointer cleanup and Delete my account can be run again. A dormant test hook (`window.__FIREBASE_EMULATORS__.fail = [step]`) forces a named step to fail in the integration tests.

## Data model (under `households/{hid}/`)
- `weights/b{i}-{YYYY-MM-DD}` → `{twin, i (0|1), date, v (g), approx, by}` — one per baby per night (weighed at 8 PM).
- `feeds/b{i}-{epochMs}` → `{twin, i, t, v (mL PO), note, diet, by}` — one per baby per fixed feed slot. `v:0` with note `All by tube` / `Skipped` marks a non-PO feed; notes matching `MARK` (`est.`, those two) are replaced when a value is re-entered.
- `config/profile` → `{born, ga, schedule:{everyH (2|3|4), startH (0–12)}, twins:[{name, birthTime, birthG, fullMl, slotMin, color}]}` — `color` is a PALETTE key (pink, purple, blue, orange, green, teal) with light/dark/night variants.
- `config/diet` → `{text}`; stamped onto each new feed.
- `pumps/p-{epochMs}` → `{t, v (mL), by}` — mom's pump sessions. `drops/d-{epochMs}` → `{t, v, by}` — milk taken to the NICU.
- `config/people` → `{list:[{email, name}]}` — display names shown as "by" on entries (fallback: email initial). Store stamps `by` = signer's email unless the record already carries one (restores/edits keep the author).
- `checklist/{b0|b1|f}-{key}` → `{s:"done"|"na", d:YYYY-MM-DD, by}` — discharge checklist (`DIS_BABY` per baby by index, `DIS_FAM` for parents). Absent doc = not done.
- `plans/{idx}-{feedDay}` → `{i, day, text, by}` — one-line plan from rounds per baby per feed day.
- `questions/q-{epochMs}` → `{text, done, t, doneT, ans, by}` — questions for rounds.
- Every baby-keyed record uses the baby's index (`i`, 0/1); `twin` is only a readable label. Older docs keyed `{Name}-…` without `i` are still read (`twinOf`: index → current name → a former name in `profile.twins[n].aka`) and get `i` stamped in place (`upgradeIndex`, same ids, nothing deleted). Renaming only updates the profile and adds the old name to `aka` — no data moves, and a phone that was offline during a rename can't orphan entries.
- Full backup (Settings → Data): one JSON file `{app:"twins-tracker", format:2, data:{<every Store.lists.shared collection incl. events, needs>, config:{profile, diet, people, milk}, private:{checkins:{…}}}}` (raw docs by id; `private` holds only the signed-in person's own data, from `RAWP`). Restore is merge-only (adds missing ids/config, never changes or deletes), accepts `app` `twins-tracker` or `niculog` and `format` 1 or 2 (other formats refused in plain language), and writes private items only through `Store.putPrivate` (the signer's own subtree). Older app versions ignore the new keys. `events`/`needs` are watched in `startData` only so backups carry them (no UI yet). The CSV export is unchanged.
- Dates: one short style `mdD` "Feb 10" and one long style `longD` "Tue, Feb 10"; Records groups rows under day headers with times in the When column.
- `config/milk` → `{count, t}` — NICU's actual stock count at time t (overrides drop-off math from then on).
- Milk math (assumes babies get only mom's milk): need/day = Σ fullMl × 8; NICU stock ≈ (count or 0) + drop-offs since − fullMl for every scheduled feed slot since (`usedSince`), stepping down at each feed time.

## Design system (Phase 0)
- All colours, spacing (`--sp-1..6`, 4-pt), radii (`--r-xs..lg`, `--r-pill`), elevation (`--shadow-1/2`) and type sizes (`--fs-*`) are CSS tokens at the top of `<style>`; components use tokens only.
- Brand: navy `#193653` for titles and the brand mark only (`--title`, `--brand`); medical blue `#3976A8` is the action colour (`--accent`: buttons, FAB, pressed chips) and links/focus; supporting blue `#6C8FAD`. Status tokens come as base / `-ink` (text) / `-tint` (backgrounds): success `#24836B`, warning `#B77928`, danger `#B94A48`.
- Light text: `--text` `#182B3A`, `--title` navy, `--text2` `#637587` (on cards), `--muted` `#5A6D80` (small text anywhere, incl. the page background where #637587 is <4.5:1).
- Themes: light, dark (Appearance = Dark, or System + phone in Dark mode; `data-look`), night (`data-theme=night`, manual or auto; blue-black with warm text). Every text pair ≥4.5:1, field borders ≥3:1 in all three.
- Twin identity: `PALETTE` keys unchanged (pink, purple, blue, orange, green, teal), muted values per theme [light, dark, night], each ≥4.5:1 on its surface. Identity is never colour-only: names always shown, selector names wrap rather than truncate.
- Shell: brand mark + eyebrow + baby names, sync pill (success/warning/danger tint), segmented baby selector (tinted track, selected = raised white chip with navy text, colour dot + name), tab bar with pill highlight behind the active icon. Tab ids unchanged.
- `tests/screens.js <dir>` saves iPhone-size (390×844 @2x) screenshots of every tab in light/night, each baby, A++ text and offline, for before/after design review.

## Domain rules
- A day runs `dayH` to `dayH` (default 7 AM–7 AM, matching NICU shifts) and never depends on feed times. Feeds every `everyH` h (default 3) on the grid anchored at `startH` (default 8 AM); `setSchedule` builds `SLOT_H` (hours within the day window), `FEEDS_PER_DAY`, `DAY_START_H`. Each baby offset by `slotMin` (0 or 30). Daily totals count feeds by clock time (`feedDay`), so changing feed times never moves the day.
- Only PO volume is tracked. Full feed default = 150 mL/kg/day × birth weight ÷ 8, overridable per baby.
