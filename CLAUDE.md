# NICUlog (formerly Twins Tracker) — context for Claude

Static PWA (no build step) for parents to chart twin NICU babies' nightly weights and PO feeds. Hosted on GitHub Pages from `main` / root. Backend: Firebase Auth (email/password, sign-up allowed) + Firestore. Multi-family: each family's data lives under `households/{hid}`; both parents join the same family with an invite code.

**This repo is public. Never commit names, birth dates/times, weights or any feed data.** All personal details live in Firestore (`households/main/config/profile`), entered on the in-app setup screen.

## `window.Store` contract (`firebase-store.js`; same contract in `tests/stub-store.js`)
- **Writes:** offline cache on; a write resolves after the server ack or 1.5 s, whichever is first, so the UI never hangs. A later rejection is reported as a `store-error` event.
- **Collection names live in one place:** `SHARED`, `PRIVATE`, `CONFIG`, `META`, `MEDIA`, exposed as `Store.lists` (`{shared, private, config, meta, media}`).
- **Two method styles, both current (documented, not merged — ledger P1-07):**
  - Older per-collection methods: `watchWeights`, `watchFeeds`, `setWeight`, `delWeight`, `setFeed`, `delFeed`, `watchDiet`, `setDiet`, `watchProfile`, `setProfile`.
  - Generic methods: `watch(name, cb, err)`, `put(name, id, rec)` (stamps `by` = signer's email unless present), `remove(name, id)`, `watchConfig(name, cb, err)`, `setConfig(name, v)`.
- **Phase 1 additions:** `patch(name, id, fields)` — merge only those fields into an existing family doc (`updateDoc`; fails / `store-error` rather than recreating a doc the other parent deleted; `by` is stripped so authorship never changes). `watchPrivate` / `putPrivate` / `removePrivate` — like `watch` / `put` / `remove` but under the signer's own `private/{auth uid}/{name}` (uid always from Firebase Auth; `putPrivate` stamps `by` unless present). `removePrivate` undoes a just-saved check-in.
- **Photo additions (Phase 5):** `putPhoto(id, meta, full)` (one batch: `photoData/{id}` `{full}` + `photos/{id}` meta with `thumb`, `by` stamped; bytes cross the boundary as `Uint8Array`); `watchPhotos(evIds, cb, err)` (metadata + thumbnails for those moments only, `where ev in`, ≤30 ids per listener); `photoFull(id)` (full image on demand; `null` if absent or offline and never loaded); `markPhoto(id, t|null)` (soft-delete marker / Undo); `purgePhoto(id)` (image first, metadata last); `photoUsage()` (server aggregate `{n, bytes}`; needs a connection). Stub: `__TEST_PHOTO_OFFLINE` makes `photoFull` find nothing.
- **Families:** `family()`, `createFamily()`, `joinFamily(code)`, `familyInfo()` (lenient), `newInvite()`, `removeMember(uid)`, `leave()`, `deleteAccount(password)`.
- **Milk-source additions:** `create(name, id, rec)` (history entries; create-only by the rules); `guardedPut(name, id, rec)` (full write; on a rules refusal it reads the server copy: identical → `{saved, already}` (lost acknowledgement), else `store-error` code `conflict` carrying `current` and `mine`; resolves `{pending}` offline after 1.5 s); `activateSources(v)` (see Milk sources); `markClient(v)`; `uid()`.
- **Test hooks (dormant in the app):** `window.__FIREBASE_EMULATORS__` (set only by the emulator tests) points the Store at the local emulators; `.fail = [step]` forces a named lifecycle step to fail. The stub keeps private data per user (`__db.private[uid]`), simulates removal (`__TEST_REMOVED`, `__TEST_CLEANUP_FAILS`), enforces the same milk-source validators and rev check (`__TEST_WRITES`, `__TEST_HOLD` for queued/offline writes), and can simulate an offline activation (`__TEST_OFFLINE_ACTIVATE`).
- **App test hooks:** `window.__nicu` (`buildTimeline`, `validEvent`) and `window.__nicu.src` (the milk-source logic API) are marked TEST HOOK in the code; they grant nothing the screens and rules don't already allow (ledger P1-09).

## Families
- `users/{uid}` → `{hid}` (which family this sign-in uses). `households/{hid}` → `{owner, code, codeExp (ms), created}`. `households/{hid}/members/{uid}` → `{email, t, code?}`. `invites/{CODE}` → `{hid, exp}` (get-only lookup, 8 chars from an unambiguous alphabet, 7 days).
- `Store.family()` resolves the family after sign-in: users doc → membership check; else claims `main` (allowlisted emails); else null → the app shows `#family` (join with code / start a new family). Offline it reopens the cached hid; a permission refusal on `users/` throws code `denied` (banner: "This account can't open the tracker…"), never opens another family.
- Settings → Family card: members (you / owner), invite code with Share + New code, Remove (owner), Leave, Delete my account (re-auth; the last member out deletes all the family's data). Ownership passes to another member when the owner leaves.
- **Not enforced by the rules (documented decisions, ledger P2-03 / P2-04):** authorship (`by`, `createdT`) can be rewritten by any member; the older collections (feeds, weights, pumps, drops, checklist, plans, questions, needs, config docs) have no shape validation — the app cleans them on read. Revisit in Phase 6 if NICUlog is offered to other families.
- **Rules:** data readable/writable only by members (or allowlisted emails for `main`); join only as yourself with the current unexpired code, with a membership record of exactly `{email, t?, code?}` whose email is your own sign-in email, lowercased (`validMember`); members can't be edited; only the owner removes others or deletes the family record. The shared-data catch-all excludes `members`, `private`, `revoked`, `photos`, `photoData`, `events`, `slotMilk`, `milkUsual`, `schedPeriods`, `clients` and `config` (each has its own rule; every config doc except `sources` keeps the catch-all's members-only rule).
- **Legacy revocation:** removing a member of `main` writes `households/main/revoked/{email lowercased}` (only the owner can create, update or delete it; members and the revoked person can't); `legacy()` ignores revoked emails, so the allowlist can't readmit them (claim, data access, creating the family record). The owner can still deliberately re-invite them with a code: the revocation stays in place and their membership grants access while invited; removing them again rewrites the revocation (owner update) and deletes the membership.
- **Private subtree** `households/{hid}/private/{uid}/{name}/{doc}` (Phase 3 check-ins; `Store.lists.private` = `["checkins"]`): only the uid in the path can touch it — never the other parent, strangers, or the legacy allowlist. Read/list and delete need only "my uid" (the removed-member cleanup exception); create/update also need current membership.
- **Lifecycle (D10: a leaving or removed member's private data is deleted):**
  - `purgePrivate(hid, uid)` deletes the signer's own private docs (server reads, explicit list, verifies empty).
  - Lifecycle decisions use `familyStrict()` (server reads, errors propagate) — never the lenient `familyInfo()`.
  - `leave()`: purge → transfer ownership → delete own `clients` marker → delete membership → delete pointer (pointer last, so a part-way failure is finished by the next open).
  - `removeMember(uid)` (owner) fails closed in this order: publish a new invite code and read it back from the server (`rotateInvite(true)`; changing the family's code is what invalidates the old one) → delete the old invite doc → `main` only: write the revocation → delete the membership. Any error stops before access is revoked.
  - `family()`: membership is checked with `getDocFromServer`; if it can't be confirmed (offline/error) nothing is deleted and the cached family reopens; if confirmed removed → purge own private data → delete `users/{uid}` → return null. If the purge fails it throws `cleanup-pending` (banner) and keeps the pointer, so the next open retries.
  - `deleteAccount` fails closed: no swallowed errors; the Firebase Auth user is deleted only after all Firestore cleanup succeeded. Last member: purge → every `SHARED`, `MEDIA` and `META` collection → config (incl. `sources`) → invite (if it still exists) → revocations + family record (if it exists) → membership → pointer → auth user. Otherwise `leave()` then the auth user. Every step is safe to repeat; if the membership is already gone, the next open's `family()` finishes the pointer cleanup and Delete my account can be run again.

## Data model (under `households/{hid}/`)
- `weights/b{i}-{YYYY-MM-DD}` → `{twin, i (0|1), date, v (g), approx, by}` — one per baby per night (weighed at 8 PM).
- `feeds/b{i}-{epochMs}` → `{twin, i, t, v (mL PO), note, diet, by}` — one per baby per fixed feed slot. `v:0` with note `All by tube` / `Skipped` marks a non-PO feed; notes matching `MARK` (`est.`, those two) are replaced when a value is re-entered. Feed saves, note edits and Undo keep fields this version doesn't know (`extraF`).
- `config/profile` → `{born, ga, schedule:{everyH (2|3|4), startH (0–12)}, twins:[{name, birthTime, birthG, fullMl, slotMin, color, home?}]}` — `color` is a PALETTE key (pink, purple, blue, orange, green, teal) with light/dark/night variants. `home` (epoch ms, optional) = when that baby went home; see Discharge.
- `config/diet` → `{text}`; stamped onto each new feed.
- `config/people` → `{list:[{email, name}]}` — display names shown as "by" on entries (fallback: email initial; in sentences, "The other parent" via `whoSays`). The Store stamps `by` = signer's email unless the record already carries one (restores/edits keep the author).
- `config/cams` → `{links: {"0"?: url, "1"?: url}}` — bedside-camera links per baby index (product owner, Nov 20, 2026): https only (`CAM_OK`), set in Settings → Baby cameras or on the setup screen (`suK0/1`); backed up (`BK_CFG`), deleted with the family (`CONFIG`); no rules change (config members-only rule). NICUlog only opens the link. A link saved on a phone by the first version (localStorage `camLinks`) moves here once, then leaves the phone.
- `config/milk` → `{count, t}` — NICU's actual stock count at time t (overrides drop-off math from then on).
- `pumps/p-{epochMs}` → `{t, v (mL), by}` — mom's pump sessions. `drops/d-{epochMs}` → `{t, v, by}` — milk taken to the NICU. New ids get a 4-char random suffix (`p-{epochMs}-xxxx`) so two entries in one minute both save; old ids are untouched.
- `checklist/{b0|b1|f}-{key}` → `{s:"done"|"na", d:YYYY-MM-DD, by}` — discharge checklist (`DIS_BABY` per baby by index, `DIS_FAM` for parents). Absent doc = not done.
- `plans/{idx}-{feedDay}` → `{i, day, text, by}` — one-line plan from rounds per baby per feed day.
- `questions/q-{epochMs}` → `{text, done, t, doneT, ans, by}` — questions for rounds.
- `events/e-{epochMs}-{rand4}` → `{kind: "milestone"|"journal"|"moment", scope: "baby"|"parent"|"family", i: 0|1|null, key, t, title (≤120), note (≤2000), ref: {col,id}|null, src: "checkin"|null, by, createdT, editT, editBy}` — Journey moments. `i` required for scope baby, null otherwise; `src` is only a provenance marker (Phase 3 shared check-ins), never an id. Validated identically in the app (`validEvent`/`cleanE`) and in `firestore.rules` (`validEvent`). Content (milestone catalog, firsts and date-milestone rules, wording) comes from `docs/phase2-catalog.md`.
- `photos/ph-{epochMs}-{r4}` → `{ev (event id), t, w, h (≤1600), bytes (image + thumbnail), thumb: Bytes (~320 px JPEG, ≤100 KB), by, deletedT?}` and `photoData/{same id}` → `{full: Bytes (≤1600 px JPEG, ≤900 KB)}` — Phase 5 photos on moments (D3/D4), up to 6 per moment (app-enforced; rules can't count). Encoded on the phone (`encodePhoto`: `createImageBitmap` → canvas → JPEG, which drops location/camera metadata). Rules (`validPhoto` / `validPhotoData`): exact fields, sizes, `by` = signer, the moment exists, the image is written in the same batch (`existsAfter`); the only update is `deletedT`; `photoData` is never edited. Only the moments on screen are watched (`syncPhotoWatch`); full images load when opened. Delete = `markPhoto` + Undo, then this phone purges after the Undo time (`phPurgeLater`); deleting a moment does the same for its photos; anything marked for over 10 min is purged by whoever sees it. JSON backup carries photo metadata only (`data.photos`, read when Settings opens; restore ignores it); not in `Store.lists.shared`. Settings shows `Photos: N · about X MB of the 1 GB free storage` (`photoUsage`). Deferred (product owner, Nov 19, 2026): check-in photos and the ZIP "backup with photos".
- `private/{uid}/checkins/c-{epochMs}-{r4}` → `{t, mood (1–5), note (≤120), sharedEv: event id | null, by}` — Phase 3 private check-ins (owner-only subtree). Shown only on the author's Support screen (`CI`, from `RAWP`); never on any other screen, in the timeline, CSV or the partner's backup. Sharing (D6/D13/D14): `putPrivate` records `sharedEv` first (content untouched, unknown fields kept), then `Store.put("events", sharedEv, copy)` — copy = `{kind:"journal", scope:"parent", i:null, key:null, t, title:"{word} today", note, ref:null, src:"checkin"}` with a fresh id that carries nothing of the check-in's. Unshare: remove the copy, then clear `sharedEv`. "Shared" shows only when the copy exists (`ciShared`); a recorded id with no copy offers Share again, which reuses the id, so there is never a second copy.
- `needs` — dormant: the Phase 4 needs list was dropped (product owner, Nov 19, 2026); no screen and no writer; watched only so backups carry it (ledger P1-10).
- **Baby identity:** every baby-keyed record uses the baby's index (`i`, 0/1); `twin` is only a readable label. Older docs keyed `{Name}-…` without `i` are still read (`twinOf`: index → current name → a former name in `profile.twins[n].aka`) and get `i` stamped in place (`upgradeIndex`, same ids, nothing deleted). Renaming only updates the profile and adds the old name to `aka` — no data moves, and a phone that was offline during a rename can't orphan entries.
- **Full backup** (Settings → Data): one JSON file named `niculog-backup-{date}.json`, `{app:"twins-tracker", format:2, data:{<every Store.lists.shared collection>, config:{profile, diet, people, milk, cams}, private:{checkins:{…}}}}` (raw docs by id; `private` holds only the signed-in person's own data, from `RAWP`). Restore is merge-only (adds missing ids/config, never changes or deletes), accepts `app` `twins-tracker` or `niculog` and `format` 1 or 2 (other formats refused in plain language), and writes private items only through `Store.putPrivate` (the signer's own subtree). Older app versions ignore the new keys. `clients` and `config/sources` are never backed up.
- **CSV export/import:** existing columns unchanged, plus three trailing milk-source columns (see below).
- **Dates:** one short style `mdD` "Feb 10" and one long style `longD` "Tue, Feb 10"; Records groups rows under day headers with times in the When column.

### Discharge (one baby went home)
- Set in Settings → babies ("Went home", datetime; must be between birth and now); clearing it means she's back in the NICU. Stored as `profile.twins[i].home` (no new collection, no rules change; backed up with the profile).
- Helpers: `homeAt(tw)`, `inNicu(tw, t)`, `wentHome(tw)`. From that time on she leaves daily tracking: Today shows "went home on …" in place of her card; the day sheet shows her only for feed days that began before she left; Growth shows "Home" (no entry box) for later nights without a weight; Progress shows the went-home line instead of her markers; Journey offers the "Came home" milestone (key `came-home`, dated when she went home).
- Milk estimate: her scheduled feeds stop counting from that time (original path: `usedSince` / `feedsSince` / `nextUse` / `legacyNeed` check `inNicu`; engine path: `srcState().until` → `MilkSources` `usage` / `nextDraw` / `needPerDay10`). Everything before she went home is unchanged.
- Her history (Records, Growth, Journey, backups, CSV) is kept; nothing is deleted.

### Milk sources (design: `docs/phase2b-design.md`, approved Stage A rev 3, D-1–D-8)
- **Amounts** are integer tenths of a mL. *Actual* (what was recorded: `feeds.v`, an allocation's parts) is never changed by the calculation; *scheduled* (a baby's scheduled feed amount at a scheduled occurrence) is the stock basis. At each occurrence the stock is charged scheduled × the mother's-milk share (largest-remainder split, ties mother's → donor → formula; parts always total exactly).
- `slotMilk/b{i}-{t}` → `{i, t (occurrence ms), state "set"|"usual", mL10 {mom,donor,formula}|null, total10|null, basis "feed"|"scheduled"|null, rev, by, editT, editBy}` — per-occurrence allocation. Parts total exactly the reference: the logged by-mouth `v` (basis feed, ≤ 1500 = the 150 mL entry limit) or the scheduled amount (tube/skipped/unlogged). Rules: create when absent; update only with `rev` = stored + 1 and `editBy` = signer; "use usual milk" is an update, not a delete.
- `milkUsual/u-{i}-{from}-{r4}` → `{i, from, pct {mom,donor,formula} (ints, total exactly 100) | null, by}` — append-only usual-milk history, from = save time (never backdated); latest `from ≤ t` wins (ties: greater id).
- `schedPeriods/s-{from}-{r4}` → `{from, everyH, startH, dayH, slotMin[2], full10[2], src "first-use"|"setup"|"observed", by}` — append-only schedule history. Written only once a family uses sources: the first source write adds a `first-use` period from 0 equal to the current profile (no number changes); after that, a setup save that changes feed times or a full-feed amount adds a `setup` period from now, so earlier occurrences keep their schedule and scheduled amount.
- `clients/{uid}` → `{v, t}` — the app version reported by each **member account** (`MilkSources.CLIENT_V`); never backed up (`Store.lists.meta`). Naming note (ledger P1-08): the stored names `clients` and the activation field `phones` mean member accounts, not devices; the marker is self-reported by that account's app, not proof of what any device runs (no App Check).
- **Activation (enforced by the rules):** tracking is ON only when `config/sources` → `{on:true, t, by, phones:[uid…]}` exists (`srcOn()` also requires `phones`). `ensurePeriods()` calls `Store.activateSources(v)` first (before any first-use period); it reads the complete member list **from the server** (`familyStrict`) and names every member account; errors `offline` / `not-ready` / `too-many` (> 4). Rules (`match /config/sources`, `validActivation` / `accountReady`): create-only by a member; exact fields; `by` = signer; 1–4 accounts incl. the signer; each named account must be a current member whose own `clients` marker is at v ≥ 1; no update; delete by `inFamily` (only switches tracking off; source data untouched). One-member families can activate.
- **Accepted limits:** an old app version doing the last member's account deletion doesn't know the milk-source collections and would leave them behind (ledger P2-05; current versions delete everything). Rules can't list `members`, so a direct write could omit a member — the app always names all; a member who joins later isn't in `phones` and Care says so ("joined after milk sources were turned on"), never as activated. Care refreshes the member list whenever Care or Settings opens.
- **Restore:** `config/sources` is not in `BK_CFG`, so a restore brings source data back intact but dormant: Care says so and offers "Turn on milk sources" once everyone has the updated app (restored periods/usual keep their original dates; no first-use period is added if periods exist). `CONFIG` includes `sources` for last-member deletion.
- **Resolution per occurrence:** allocation "set" → its proportions; else usual milk in effect → its pct; else Not recorded → whole scheduled amount as mother's (the original behaviour). Tube, skipped and unlogged occurrences resolve the same way.
- **Unconfigured families** (tracking never turned on) run the original estimate code untouched — including the original retroactive re-run after a schedule change. Configured families: `usedSince` / `feedsSince` / `nextUse` / `need` go through the engine.
- **Feed-follow:** after a feed save/clear/Undo, a single-source allocation follows the new reference; a mixed one is left as a mismatch. Allocations whose time a schedule change removed are kept, not counted (`stranded`). An old-app schedule change (profile ≠ period in effect) is reported by `scheduleDrift()`; no period is written and no effective time assumed until a parent confirms (`recordPeriod(from, "observed")`).
- **Screens:**
  - Care card `#srcCare`: member list with each account's app status (`memberList`), who turned sources on and who is included, usual milk per baby (Mother's / Donor / Formula / Mixed % / Not recorded) with a live mL preview on the current scheduled amount, Undo via `undoUsual`.
  - Today: `.srcline` "Milk: … ›" on each card's slot. Source sheet `#sSheet`: one tap per source = the whole reference; Mixed… mL boxes must total the reference exactly; "Use usual milk"; mismatch warning.
  - Records: source line per feed (`.srcbtn`), rows for allocations on unlogged feeds and stranded ones (Remove + Undo).
  - Milk tab: working by source (`srcCalc`: usual / per-feed / Not recorded, mixed, not-counted donor/formula; parts in tenths add up exactly), Need / day (mother's milk); every division by need is guarded (0 = "no mother's milk planned"); chart legend/line follow it.
  - Journey summary adds the source only when `MS.oneSource` says the whole day was one source.
  - Setup confirm names upcoming sources a feed-time change would strand. Drift card `#srcDrift` (Milk tab) + Today notice: shows both schedules, asks when the new times started (no default), records an `observed` period only on Confirm.
- **Conflicts:** an app-guard conflict (sheet showed an old rev) or a server refusal (`store-error` code `conflict`) is kept in localStorage `srcConflicts:{uid}` until a parent chooses Keep theirs / Use mine (Today notice `#srcNote`, review in `#sSheet`); "theirs" is the newer of the server copy and the synced one; Use mine waits until theirs has synced. Offline saves say "Saved on this phone. It will sync when you're back online."
- **Logic API** (screens and tests): `window.__nicu.src` — `setUsual`, `undoUsual` (delete only if no occurrence passed, else append a restoring entry), `setAlloc(i, t, mL10|null, seenRev)` (returns `{conflict}` when the stored rev ≠ the shown one, `{error:"mismatch"}` when parts don't reconcile), `singleAlloc`, `recordPeriod`, `scheduleDrift`, `sourcesReady`, `stranded`, `usage`, `parts`.
- **Backup and CSV:** the three collections ride along in `Store.lists.shared` (merge-only restore keeps `rev`). CSV adds three trailing columns `milk_mother_ml, milk_donor_ml, milk_formula_ml` (actual parts; blank when usual/not recorded); import creates an allocation only if none exists and it reconciles.
- **Milk math when sources are off** (assumes babies get only mom's milk): need/day = Σ fullMl × feeds per day; NICU stock ≈ (count or 0) + drop-offs since − fullMl for every scheduled feed slot since (`usedSince`), stepping down at each feed time.

## UI layout
### Shell
- Sticky top: title + sync status (Synced / Syncing… / Connecting… / Offline, from snapshot `fromCache`/`pending` + navigator.onLine), night-mode toggle (amber-on-black, per device), view bar (twin 0 | twin 1 | Both) that filters every screen.
- Bottom tab bar (D1): Today · Growth · Milk · **Journey** · **More** — ids `feed`, `weight`, `milk`, `trends`, `more` unchanged (stored `tab` values stay valid). Tab, view and night mode are remembered in localStorage.

### Behaviours
- Overwrite guard: Today cards, the feed sheet and the weight grid remember what each box showed (`data-had` / `fSig` / `wSig`); if the entry changed since and the other parent made it, saving asks before replacing it. Undo asks before replacing a change the other parent made after your save (undo fns may return false to cancel).
- Checklist snapshots patch rows in place (`patchChecklists`, containers carry `data-ids`) instead of a full re-render, and `renderAll` restores scroll, so taps never move the screen.
- A feed arriving from the other parent (by ≠ me, within 3 h) flashes "<name> logged …".
- Every save/delete shows an 8 s Undo bar. Amounts >130% of full feed or far from the recent average ask to confirm. Saving setup with changed feed times asks first.
- Per-phone prefs (localStorage `prefs`): appearance `look` system|light|dark (sets `data-look`; system follows `prefers-color-scheme`; night overrides), units g|lb (display only; entry stays grams), clock 12|24, text size via CSS zoom (cards restack with container queries), night manual|auto 9 PM–7 AM.
- Floating "+ Log feed" button on Growth/Journey, or on Today once the Next card scrolls away (hidden on Milk/More); it tucks away (`.tuck`) while scrolling down and returns on any scroll up.
- Charts render only when their tab is visible (`draw` skips hidden canvases; `showTab` re-renders). Chart callouts close on a tap elsewhere, on scroll, or after 5 s (`hideTips`). Diet changes (from feeds' `diet`) draw dotted markers on the PO and daily charts.
- `#upd` "New version ready — tap to refresh" shows on `controllerchange` when the page was already controlled (https only).
- Every control is ≥44 px tall (tested). No text below 12 px. Records table becomes two-line rows under a container query at large text; growth grid boxes flex. Sign-in and setup screens carry the brand mark. Error text is plain language (no rules/allowlist jargon).

## Design system
- All colours, spacing (`--sp-1..6`, 4-pt), radii (`--r-xs..lg`, `--r-pill`), elevation (`--shadow-1/2`) and type sizes (`--fs-*`) are CSS tokens at the top of `<style>`; components use tokens only.
- Brand: navy `#193653` for titles and the brand mark only (`--title`, `--brand`); medical blue `#3976A8` is the action colour (`--accent`: buttons, FAB, pressed chips) and links/focus; supporting blue `#6C8FAD`. Status tokens come as base / `-ink` (text) / `-tint` (backgrounds): success `#24836B`, warning `#B77928`, danger `#B94A48`.
- Light text: `--text` `#182B3A`, `--title` navy, `--text2` `#637587` (on cards), `--muted` `#5A6D80` (small text anywhere, incl. the page background where #637587 is <4.5:1).
- Themes: light, dark (Appearance = Dark, or System + phone in Dark mode; `data-look`), night (`data-theme=night`, manual or auto; blue-black with warm text). Every text pair ≥4.5:1, field borders ≥3:1 in all three.
- Twin identity: `PALETTE` keys unchanged (pink, purple, blue, orange, green, teal), muted values per theme [light, dark, night], each ≥4.5:1 on its surface. Identity is never colour-only: names always shown, selector names wrap rather than truncate.
- Shell: brand mark + eyebrow + baby names, sync pill (success/warning/danger tint), segmented baby selector (tinted track, selected = raised white chip with navy text, colour dot + name), tab bar with pill highlight behind the active icon.

## Domain rules
- A day runs `dayH` to `dayH` (default 7 AM–7 AM, matching NICU shifts) and never depends on feed times. Feeds every `everyH` h (default 3) on the grid anchored at `startH` (default 8 AM); `setSchedule` builds `SLOT_H` (hours within the day window, via `MilkSources.slotHours`), `FEEDS_PER_DAY`, `DAY_START_H`. Each baby offset by `slotMin` (0 or 30). Daily totals count feeds by clock time (`feedDay`), so changing feed times never moves the day.
- A logged feed belongs to a feed time if it's at that time, else the nearest one within the stray window (half an interval, at most 90 min; ties go to the earlier): `feedNear`, used by `slotFeed` (day sheet, Today, missed feeds, Journey firsts) and `feedAt` (milk sources).
- `profileReady()` is false until `applyProfile` has run (`profileApplied`), and again after sign-out. Once a profile has loaded in a session, a "missing profile" snapshot is ignored (a stale listener reading seen right after the first setup save; nothing deletes the profile while anyone is signed in) — it never sends the app back to setup.
- Only PO volume is tracked. Full feed default = 150 mL/kg/day × birth weight ÷ feeds per day, overridable per baby.
