# Twins Tracker: update since the Phase 4 audit (Nov 15, 2026)

Context for ChatGPT: I'm building this app with Claude Code (it writes and tests the code). This is everything done and decided since the Phase 4 quality audit, plus where App Store readiness stands. Please base new feature proposals on the current state below, especially the data model, the family accounts model and the product rules.

## Product rules (unchanged, still binding)
- A family tracking aid only: no medical advice, no clinical thresholds, nothing that claims or implies discharge readiness. The Progress tab says "family tracking indicators, not clinical discharge criteria; the NICU team decides" and uses neutral "Marker reached" / "Not yet" chips (no green checks).
- Twins only (two babies per family, Baby A / Baby B). Only by-mouth (PO) volume is tracked. Full feed = 150 mL/kg/day × birth weight ÷ 8, can be overridden per baby, and stays based on birth weight (the NICU doesn't recalculate it).
- A day runs 7 AM to 7 AM (NICU shifts, configurable) and never depends on feed times.
- The code repo is public, so no real names, birth details or data ever go in code or tests. Personal data lives only in the database.
- Built for one-handed use at 2 AM: every control is at least 44 px, three themes (light, dark, night), large-text support, works offline.

## Tech in one paragraph
A single-file static web app (`index.html`, no build step, Chart.js) hosted on GitHub Pages, with a Firebase backend (email/password auth and a Firestore database with offline cache). All data access goes through one `window.Store` interface (`firebase-store.js`). There's a 152-check automated browser test suite with a fake in-memory backend, plus a separate 28-check test suite for the database security rules, run on Firebase's local emulator. A new iOS wrapper project (Capacitor) lives in `native/`.

## 2. The "not done" audit items, now done properly
- **Renaming a baby can't lose data:** every record is tied to the baby's position (Baby A = 0, Baby B = 1), not the name. A rename only updates the setup and remembers the old name. Entries saved under an old name, even from a phone that was offline during the rename, still show. Older records were upgraded in place; nothing was moved or deleted.
- **Full backup and restore:**
  - Settings → Data saves one file with everything: feeds, weights, pumping, drop-offs, NICU count, checklists, rounds plans, questions and setup.
  - Restore only adds what's missing and never changes or deletes existing records.
  - The spreadsheet (CSV) export is unchanged.
- **Consistent dates:** one short style ("Feb 10") and one long style ("Tue, Feb 10"). Records are grouped under day headings.

## 3. Family accounts (for multi-family / App Store use)
- **Accounts:** anyone can create an account. Each family's data is completely separate.
- **Joining:** one parent starts a family, and the other joins with an invite code from Settings. Codes are 8 characters, last 7 days and can be renewed. Shared through the phone's share sheet.
- **Settings → Family:**
  - Member list (marked "you" / "owner").
  - The owner can remove a member; anyone can leave.
  - **Delete my account** asks for your password. If you're the last member, it deletes all the family's data.
  - Ownership passes to another member if the owner leaves.
- **Security rules:** only family members can read or write; joining needs the current, unexpired code; strangers can't see, join or list anything. 28 emulator tests, including a deliberately weakened rule to prove the tests catch it.
- **Existing family:** my wife's and my original data stays where it is. Our two accounts are moved into the new setup automatically on first open.
- **Not yet verified end to end** on live Firebase (the rules are tested; the live sign-up/join flow isn't yet).

  - Capacitor 6 project in `native/`; iPhone only, portrait only.

## 6. Open decisions / known limits
- **Original family edge case:** the two allowlisted emails can always rejoin the original family. Removing one of them in Settings doesn't fully revoke their access unless the allowlist in the rules is edited.
- **Two babies per family:** the data model and UI assume twins. Supporting singletons or triplets would be a real change, not a setting.
- **Feed reminders / notifications:** don't exist yet. In the iOS app, local notifications would be the natural first native feature (they also help with the 4.2 review risk).

## 7. How to propose new features so they fit
Please specify each feature against these rules:
- **Data:**
  - Everything lives under the family (`households/{familyId}/…`).
  - Baby-specific records use the baby index (0/1), never the name.
  - Each record stores who entered it (`by`).
- **No new hard dependencies:** offline-first, works at 2 AM one-handed, 44 px controls, all three themes, large text.
- **No clinical claims or thresholds:** label estimates as estimates.
- **Two parents editing at once:** say what happens if both edit the same thing (the app already guards overwrites and undo).
- **Backups:** say whether it needs to be added to the full backup (any new collection should be).
- **iOS-only features:** say whether it's iOS-only (needs the native wrapper) or works in the web app too.
